## 1. 背景与目标

部门(`sys_dept`)是 ITSM 平台组织架构的载体,为以下能力提供基础数据:

1. **用户归属**:每个用户挂在唯一部门下,部门树用于用户管理的筛选与表单选择;
2. **数据权限**:角色 `dataScope=DEPT` 时,工单等业务数据按部门边界隔离;
3. **流程路由**:受理组/处理组以部门为维度分派工单(受理台 → 按部门分派);
4. **统计报表**:按部门维度聚合工单量、SLA 达成率(报表模块依赖)。

目标:提供**树形组织架构的维护能力**(查询/新增/编辑/删除/启停),保证树结构数据一致性,并与用户、角色数据权限模块正确联动。

## 2. 范围

**In Scope(V1.0)**

- 部门树查询、新增、编辑、删除、启用/停用;
- 树形结构维护(`ancestors` 祖先链);
- 与用户管理(部门下拉、按部门过滤)、角色数据权限(DEPT 范围)的联动。——这块可暂放

**Out of Scope(V1.0 不做)**

- 部门拖拽排序、部门移动(挂载关系调整)→ V1.1;
- 部门批量导入(Excel)→ V1.1(产品文档 7.10);
- 多维度组织(虚拟组、矩阵式组织)→ V2.0;
- 部门级审批人自动匹配(按部门找处理组)→ V1.1。

## 3. 用户与权限——了解即可

### 3.1 权限点(挂载于「系统管理 → 部门管理」菜单节点之下)

| 权限点 | 说明 | 控制接口 |
| --- | --- | --- |
| `sys:dept:list` | 查看部门树 | `GET /depts/tree` |
| `sys:dept:add` | 新增部门 | `POST /depts` |
| `sys:dept:edit` | 编辑部门 | `PUT /depts/{id}` |
| `sys:dept:delete` | 删除部门 | `DELETE /depts/{id}` |

### 3.2 可见性规则

- 部门管理页面入口仅对拥有 `sys:dept:list` 的角色可见(菜单按 RBAC 动态下发);
- 内置 `ADMIN` 角色代码层直通,天然拥有以上权限;
- 普通业务角色(坐席/工程师/员工)**不开放**部门管理菜单,但其用户表单、工单分派界面可调用 `GET /depts/tree` 只读消费部门数据(该接口权限点为 `sys:dept:list`,如需开放给业务角色,由管理员为其勾选该权限点)。

## 4. 数据模型——了解即可

### 4.1 表结构 `sys_dept`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGSERIAL | PK | 主键 |
| parent_id | BIGINT | NOT NULL DEFAULT 0 | 上级部门 id,`0` 表示顶级 |
| ancestors | VARCHAR(256) | NOT NULL DEFAULT '0' | 祖先链,如 `0,1,2`(含根占位 0,不含自身) |
| name | VARCHAR(64) | NOT NULL | 部门名称 |
| sort | INT | NOT NULL DEFAULT 0 | 同级排序号,升序 |
| leader | VARCHAR(64) | | 负责人姓名(V1.0 存姓名字符串;V1.1 规划改为 leader_id 关联用户) |
| phone | VARCHAR(32) | | 联系电话 |
| email | VARCHAR(128) | | 部门邮箱 |
| status | SMALLINT | NOT NULL DEFAULT 1 | 1 启用 / 0 停用 |
| created_by / created_at / updated_by / updated_at | | NOT NULL / | 审计字段(BaseDO) |
| deleted | BOOLEAN | NOT NULL DEFAULT FALSE | 逻辑删除标记(MyBatis-Plus `@TableLogic`) |

> 与《产品设计文档》8.2 的映射:设计稿 `path` = 实现 `ancestors`;设计稿 `leader_id` = V1.0 简化为 `leader` 姓名。

### 4.2 树构建规则

- 查询一次性加载全部未删除部门,内存中按 `parent_id` 归组构建树(不递归查库);
- 同级排序:`sort ASC, id ASC`;
- `DeptNode` 返回字段:`id, parentId, name, sort, leader, phone, status, children`(不含 `ancestors`/审计字段,控制载荷)。

### 4.3 ancestors 机制

- 新增:`ancestors = 父.ancestors + ',' + 父.id`;顶级为 `"0"`;
- 用途:后续按部门子树过滤数据(如 DEPT 数据权限、报表聚合)可直接 `LIKE ancestors || '%'`,避免递归;
- **一致性约束**:任何改变挂载关系的操作必须同步重算自身及全部后代的 `ancestors`(V1.0 不开放移动,见 §10 差距 2)。

## 5. 功能需求清单——需要实现FR-01~FR-06即可

优先级:P0 = V1.0 必须;P1 = V1.1;P2 = V2.0。

| 编号 | 名称 | 需求描述 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| FR-01 | 部门树查询 | 以树形展示全部未删除部门;节点含名称、负责人、状态标识;同级按 sort 升序 | P0 | 1) 打开页面全量渲染树;2) 禁用状态节点有"停用"标识;3) 空数据时展示引导(内置种子含"总部"根节点) |
| FR-02 | 新增部门 | 在指定上级下创建部门;录入名称(必填,≤64)、排序、负责人、电话、邮箱、状态 | P0 | 1) 树节点/工具栏均可发起,默认选中当前节点为上级;2) 上级不存在返回 40400;3) 成功后树刷新且新节点出现在正确位置 |
| FR-03 | 编辑部门 | 修改名称、排序、负责人、电话、邮箱、状态 | P0 | 1) 编辑时**上级部门锁定不可改**(V1.0);2) 名称/排序等更新即时生效;3) 不存在的 id 返回 40400 |
| FR-04 | 删除部门 | 删除前二次确认;后端逻辑删除(标记 `deleted=true`) | P0 | 1) 存在子部门 → 拒绝,提示"存在下级部门,无法删除";2) 部门下存在**未删除**用户 → 拒绝,提示"部门下存在用户,无法删除";3) 已逻辑删除的用户不阻止删除;4) 删除仅置标记,记录保留可恢复 |
| FR-05 | 启用/停用 | 通过编辑表单的状态字段切换 | P0 | 1) 停用后树上有明确标识;2) 停用部门不允许再新增下级部门(见 BR-06);3) 停用不影响已挂在该部门用户的历史数据展示 |
| FR-06 | 用户管理联动 | 用户表单的部门选择器消费部门树;用户列表按部门过滤;列表回显 `deptName` | P0 | 1) 用户新增/编辑弹窗部门下拉为树形(含搜索);2) 用户列表筛选"按部门"仅命中该部门(不含子部门,V1.0 明确此行为);3) 被逻辑删除的部门不出现在选择器 |
| FR-07 | 数据权限联动 | 角色 `dataScope=DEPT` 时,业务数据按部门边界过滤 | P1 | 依赖工单数据权限 Guard(V1.1 接入,设计文档 3.2);本模块只需保证 `ancestors` 正确 |
| FR-08 | 操作审计 | 新增/编辑/删除记审计字段(created_by / updated_by) | P1 | 由 BaseDO 自动填充;V1.1 接入 AOP 审计日志(产品文档 7.10) |
| FR-09 | 部门移动 | 调整部门挂载关系,重算自身及全部后代 `ancestors` | P1 | 见 §10 差距 2;移动后所有后代 `LIKE` 过滤仍正确 |
| FR-10 | 批量导入 | Excel 导入部门树(名称/上级/排序) | P1 | 模板校验、重复名提示、事务回滚(产品文档 7.10) |

## 6. 接口契约——了解即可

统一前缀 `/api/v1`,统一响应 `Result<T>`(`{"code":0,"message":"ok","data":...}`),JWT 鉴权。

| Method | Path | 权限点 | 入参 | 出参 data |
| --- | --- | --- | --- | --- |
| GET | `/depts/tree` | `sys:dept:list` | 无 | `DeptNode[]`(树) |
| POST | `/depts` | `sys:dept:add` | `DeptSaveCmd` | 新部门 `id` |
| PUT | `/depts/{id}` | `sys:dept:edit` | `DeptSaveCmd` | 无 |
| DELETE | `/depts/{id}` | `sys:dept:delete` | 路径参数 id | 无 |

`DeptSaveCmd` 示例(注释为字段说明):

```jsonc
{
  "parentId": 1,          // 必填,0=顶级
  "name": "应用运维组",     // 必填,≤64
  "sort": 2,              // 可选,默认 0
  "leader": "孙工",        // 可选
  "phone": "13800000003", // 可选
  "email": "ops@corp.com",// 可选
  "status": 1             // 可选,默认 1
}
```

主要错误码:

| code | 场景 |
| --- | --- |
| 40000 | 参数校验失败 / 存在下级部门,无法删除 / 部门下存在用户,无法删除 / 停用部门下不允许新增(规划) |
| 40400 | 上级部门不存在 / 目标部门不存在 |
| 40100 / 40300 | 未登录 / 无对应权限点 |

## 7. 业务规则清单——需关注

| 编号 | 规则 | 优先级 | 当前实现 |
| --- | --- | --- | --- |
| BR-01 | `parent_id=0` 表示顶级;顶级可存在多个(当前种子仅"总部") | P0 | ✅ |
| BR-02 | 新增时上级部门必须存在且未删除 | P0 | ✅(存在性已校验) |
| BR-03 | 新增时自动维护 `ancestors` | P0 | ✅ |
| BR-04 | 删除双保护:有子部门或部门下有未删除用户时禁止删除 | P0 | ✅ |
| BR-05 | 删除为逻辑删除,保留记录与审计 | P0 | ✅ |
| BR-06 | 停用部门下不允许新增下级部门(防止"僵尸分支"继续扩张) | P0 | ❌ 差距,待补(§10-4) |
| BR-07 | **同一上级下部门名称唯一**(大小写敏感,忽略首尾空格) | P0 | ❌ 差距,待补(§10-1) |
| BR-08 | 部门名称 ≤64 字符,电话/邮箱做基础格式提示(前端) | P0 | ✅(name 长度;格式提示前端补) |
| BR-09 | 编辑时上级不可选自身/自身后代(防循环引用) | P0 | ✅(V1.0 上级锁定,等价满足;开放移动后必须实现) |
| BR-10 | 改变挂载关系必须重算自身及全部后代 `ancestors` | P0 | ➖ V1.0 不开放移动,随 FR-09 实现 |
| BR-11 | 同级排序 `sort ASC, id ASC` | P0 | ✅ |

## 8. 异常与边界场景矩阵——需关注

| # | 场景 | 系统行为 |
| --- | --- | --- |
| E-01 | 新增时上级刚被他人删除 | 返回 40400「上级部门不存在」 |
| E-02 | 删除时其他窗口刚给该部门加了用户 | 删除请求校验用户计数,拒绝并提示 |
| E-03 | 部门下所有用户已被逻辑删除 | 允许删除(用户计数只统计未删除用户) |
| E-04 | 并发新增同名部门(同父) | BR-07 落地后依赖唯一约束兜底,返回 40900 |
| E-05 | 名称含首尾空格/全角字符 | 前端 trim 后提交;名称原样存储(不做全角归一) |
| E-06 | 试图删除根节点"总部" | 若无子部门无用户则允许(不做特殊保护;如业务需要可升级为保护规则) |
| E-07 | 逻辑删除的部门残留 `sys_user.dept_id` 引用 | 不清理(保留历史归属),用户列表回显部门名时对已删部门展示兜底文本 |
| E-08 | 树层级超深(>10 级) | V1.0 不限制层级,但 `ancestors` 字段 256 长度需监控;建议前端超 8 级给出告警提示 |
| E-09 | 未授权访问部门接口 | 无权限点 → 40300;未登录 → 40100 |

## 9. 非功能需求——了解即可

| 类别 | 需求 |
| --- | --- |
| 性能 | 树接口一次性加载;2000 节点以内构建耗时 < 100ms;前端渲染 2000 节点无明显卡顿(el-tree 懒展开) |
| 安全 | 所有写操作走权限点 + JWT;入参长度校验;MyBatis-Plus 预编译防注入 |
| 一致性 | 树操作全部 `@Transactional`;ancestors 与 parent_id 强一致(见 BR-10) |
| 审计 | created_by/updated_by 由统一填充器写入当前登录人 |
| 兼容 | 接口遵循 `/api/v1` 版本化;DeptNode 只增不改字段语义 |

## 10. 与当前实现的差距分析(整改待办)——了解即可

| # | 差距 | 影响 | 建议整改 | 优先级 |
| --- | --- | --- | --- | --- |
| 1 | **同父下部门名称可重复**:新增/编辑均未做同名校验 | 组织树出现"两个应用运维组",用户选择、分派、报表聚合歧义 | 后端 `create/update` 增加 `同 parent_id + name` 计数校验(排除自身),并建部分唯一索引 `UNIQUE(parent_id, name) WHERE deleted = FALSE`;错误码 40900 | P0 |
| 2 | **编辑接口会接受 `parentId` 但不重算 `ancestors`**(`apply()` 直接 setParentId) | 若调用方(绕过前端)修改上级,树结构错乱:节点挂在父下但祖先链仍是旧链,数据权限/报表 `LIKE` 过滤失真 | 后端 `update` 忽略入参 `parentId`(强制以库中原值回写),直至 FR-09 移动部门上线;前端编辑弹窗锁定上级选择器 | P0 |
| 3 | **前端 `DeptView.vue` 仍为 mock**(`admin.ts` 内存数据),未对接 `/depts/*` | 部门数据多端不一致,人员管理看到的部门与部门管理页不同源 | 参照 `api/user.ts` / `api/role.ts` 模式新建 `api/dept.ts` 并改造 DeptView(树组件 el-tree,操作按钮按权限点显隐) | P0 |
| 4 | 停用部门仍可新增下级 | 停用语义不完整(僵尸分支) | `create` 时校验父 `status=1` | P1 |
| 5 | 邮箱/电话无格式校验 | 脏数据 | 前端 el-form rules;后端可选 `@Email`/正则 | P2 |

## 11. 演进规划——了解即可

- **V1.1**:部门移动(FR-09,含后代 ancestors 重算与防循环校验)、批量导入(FR-10)、部门负责人改为 `leader_id` 关联用户、停用级联约束(BR-06)、操作审计 AOP 接入;
- **V2.0**:多组织/虚拟组、部门维度更细的数据权限(本部门及以下)、组织架构可视化大屏。

## 12. 验收清单

- [ ] 树接口返回按 `sort ASC, id ASC` 排序的正确树结构,不含已删除部门
- [ ] 新增部门后,`ancestors` 链正确(`父.ancestors + ',' + 父.id`)
- [ ] 新增/编辑同父重名部门被拒绝(BR-07 落地后)
- [ ] 编辑弹窗上级选择器锁定,接口忽略 parentId(BR-09 / §10-2)
- [ ] 有子部门 / 有在编用户的部门删除被拒绝且提示准确
- [ ] 已逻辑删除用户不阻止部门删除(E-03)
- [ ] 删除仅置 `deleted=true`,记录与审计字段保留
- [ ] 无 `sys:dept:*` 权限的角色访问接口返回 40300
- [ ] 用户管理页的部门选择器、过滤与部门数据同源一致(FR-06)
- [ ] 2000 节点树接口响应 < 500ms(含网络)
