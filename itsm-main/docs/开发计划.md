# ITSM 开发计划(前端 + 后端)

| 项目 | 内容 |
|------|------|
| 文档版本 | v0.1 |
| 编制日期 | 2026-10-04 |
| 依据 | 《ITSM 产品设计文档》v0.1 第 5 章(版本范围)、第 13 章(版本路线图) |
| 目标 | V1.0 MVP:跑通「提单 → 受理 → 处理 → 解决 → 关单 → 评价」闭环,SLA 可度量 |

---

## 1. 计划概述

- **节奏**:以「周」为相对计时,2 周一个迭代;V1.0 共 5 个里程碑(M0~M4),合计 10~12 周;
- **团队假设**:后端 2~3 人、前端 1~2 人、测试 1 人(人力变化时按下表 P0/P1 优先级裁剪);
- **当前基线(M0 已完成)**:
  - 后端:Maven 14 模块骨架全部编译通过(common/domain/engine + 三大 starter + 五个业务模块 + boot),统一响应/SPI 接口/枚举/Flowable 装配/SLA 时钟/表单模型/规则引擎骨架就绪,Flyway V1 基线、docker-compose 可一键起 PG+Redis;
  - 前端:Vue3 + Vite + TS + Element Plus 骨架,`http.ts` 统一解包层、登录页/看板占位页、`/api` 代理;
  - 仓库:`itsm-server/` 与 `itsm-ui/` 前后端分目录,各自 README 就绪;
- **优先级标注**:P0 = 里程碑出口必须,P1 = 可顺延至下一里程碑。

## 3. 里程碑任务分解

## 4. 前后端协作机制

| 机制 | 约定 |
|------|------|
| 契约先行 | 每迭代第 1 天冻结本迭代接口契约(OpenAPI 片段提交至 `itsm-server/itsm-boot` 的 springdoc 分组);前端按契约 + msw mock 并行开发 |
| 联调节点 | M1 末(登录/鉴权)、M2 每迭代末(工单闭环)、M3 末(SLA/通知)、M4 全量冒烟 |
| 分支模型 | `main` 保护 + `feature/*` 短分支;镜像 tag 语义化(`0.x` 阶段) |
| 数据库变更 | 一律 Flyway 增量脚本(V2 起),禁止改历史脚本;评审后合入 |
| 质量门禁 | 后端核心服务单测 ≥60%(引擎层重点);前端关键页面冒烟用例;每次合入跑全量构建 |
| 文档同步 | 接口变更同步更新 README 与设计文档第 9 章 |

## 5. V1.1 预告(M4~M5 月,全渠道接入)

- IM 连接器(飞书/企微/钉钉):消息建单 + 卡片审批;
- 邮件渠道建单(收件解析 → 统一受理台);
- 监控告警连接器(Zabbix/Prometheus Alertmanager → 自动建单、告警恢复自动关单);
- ES 检索实现补全、S3/MinIO 切换演练、Kafka/RocketMQ 接入 + Outbox 补偿任务落地;
- 移动 H5 完善、报表增强、满意度回访流程。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 表单设计器工作量超预期(前端最大项) | M2 延期 | 迭代 2 前完成技术选型(自研 vs form-create/vform 二次开发);先交付 8 个高频控件,低频控件 P1 顺延 |
| Flowable 与业务事务一致性 | 工单/流程状态漂移 | 同库同事务;关键动作幂等;每日对账任务(设计文档 14.1) |
| PG 中文全文检索效果不佳 | 知识/工单检索体验差 | pg_trgm 兜底先行;ES 作为 V1.1 增强引导 |
| 人力不足 | 里程碑延期 | 按 P0/P1 裁剪:每里程碑 P1 项可整体顺延,P0 不让步 |
| SLA 无 Redis 环境精度 | 预警延迟 | DB 扫描兜底(分钟级),已在设计文档预案内 |
| 三种部署形态验证工作量 | 发布延迟 | M4 前置:compose 形态自 M0 起持续可用,Helm 迭代 4 起开发,不留到最后 |
